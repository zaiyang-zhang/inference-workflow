Terms & teaching notes ↗

Layer: a model building block. FFN: Feed-Forward Network. Operator: one operation on tensors, such as Matmul or GELU. Kernel: a device program implementing one or more operators. HBM: High Bandwidth Memory.

Workflow: dependencies still apply. Matmul precedes GELU for each result. A kernel can load a later chunk while computing an earlier one and writing back a completed one. The memory lane combines reads and writes on one shared resource; two on-chip work buffers retain chunks until writeback. The four chunks represent independent completed output regions, with all required input reads grouped together.

Bounds: memory-bound means transfer demand exceeds compute demand at the chosen resource rates. Compute-bound means the reverse. Waits at startup and drain can occur in either case. All durations are teaching units, not measured hardware performance.

Quantization: this example changes weights only, from BF16 to INT8. Weight payload halves; activation and output bytes stay the same. On-chip dequantization adds compute work. Quantization approximates the weights, and metadata such as scales adds overhead that is omitted here.

Hardware support: the matrix-unit implementation uses an illustrative 4× compute rate for the same Matmul. A kernel or library must target the specialized instructions with supported shapes and dtypes. Speedup can stop at the memory limit.

Fusion: the example combines Matmul and GELU. Separate kernels finish and store the Matmul output before the GELU kernel reads it. The fused kernel retains each intermediate on-chip, applies GELU and writes only the final output. Arithmetic and final values are unchanged; the intermediate HBM write/read and one launch disappear. Launch overhead is not included in the displayed times.

Hardware names: NVIDIA CUDA Cores provide general arithmetic; NVIDIA Tensor Cores specialize in matrix multiply-accumulate. Google TPU matrix units are called MXUs. Apple M5 GPUs contain a Neural Accelerator in each GPU core for matrix-based ML workloads. These are examples of hardware paths, not identical units or a cross-device speed comparison.

Speculative decoding: BS 8 means eight requests, not eight draft tokens. This scripted greedy example proposes up to three tokens per active request. One causal target pass scores all candidate positions in parallel. Accept the matching prefix, discard the suffix after a mismatch, and append the target correction; an all-accepted draft can append a target bonus token. Both paths produce the same eight tokens per request. Completed lanes are masked. Verification uses a padded four-position batch.

SD timing: the two device presets keep batch size and acceptance fixed. Target pass time is the larger of weight-transfer demand and compute demand, approximating streaming overlap across a forward pass. Verification demands four times the target arithmetic per pass. Draft work and commit time are included. Spare compute can absorb verification; a compute-bound device cannot. Timings are illustrative, not a claim that BS 8 guarantees a speedup. KV-cache traffic and other overheads are omitted. Sampling requires probability-based acceptance and correction rather than greedy equality.
